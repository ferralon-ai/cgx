## About this glossary

Terms are listed alphabetically. Each entry gives a plain-language definition (1–3 sentences) followed by cross-references to the feature IDs where the term is specified and "See also" links to related glossary entries. Readers are assumed to have passing familiarity with query-language concepts; every jargon term used in a breakdown in the question cookbook is defined here.

Canonical terms must not be replaced with synonyms. If a term appears in the docs with a different name, that is an error; update doc 03 or doc 04 rather than coining a new term.

**Shipped vs. deferred.** A glossary defines the vocabulary of the design, which runs ahead of the binary. An entry whose *surface* — a subcommand, a query-language form, a predicate — is not in the shipped binary is tagged **(deferred)** in its first sentence, with what the binary does instead. An untagged entry names something you can run or query today. The tag is about the surface, not the concept: `must-pass-through` is a real, specified semantics with no way to ask for it yet.

## Terms

**abstract-method fulfillment** — **(deferred)** The mapping from a concrete method to the abstract declaration (`is_abstract = true`) it satisfies, specified as a `fulfills` edge with a derived `unfulfilled_abstract` predicate. The binary has no `fulfills` edge kind and the CQL planner rejects the `FULFILLS` edge type; it records `implements` and `overrides` edges instead. → GM-25; Source: `crates/cgx-core/src/edge.rs:18`, `crates/cgx-cql/tests/rejects.rs:7`; See also: [method resolution order (MRO)](#method-resolution-order-mro), [override](#virtual-dispatch)

**accessor override (property shadowing)** — **(deferred)** A subclass getter, setter, or property that overrides a parent accessor or shadows a parent field. The specified record is an `overrides` edge over accessor symbols plus a `shadows-field` edge; the binary has no `shadows-field` edge kind and the CQL planner rejects `SHADOWS_FIELD`. Per-member `overrides` edges exist. → GM-24; Source: `crates/cgx-core/src/edge.rs:18`, `crates/cgx-cql/tests/rejects.rs:7`; See also: [virtual dispatch](#virtual-dispatch)

<a id="acquiring"></a>**acquiring** — **(deferred)** The act of locking or opening a resource at the start of a [resource lifecycle pair](#resource-lifecycle-pair); every acquire is specified to reach a [release](#release) on every path. No acquire/release check exists in the binary. → GM-13; Source: `crates/cgx-index/src/local.rs:236`; See also: [resource lifecycle pair](#resource-lifecycle-pair), [release](#release), [exceptional class](#exceptional-class)

<a id="agnostic-matching"></a>**agnostic matching** — `cgx search --agnostic`: match a [selector](#selector) against every language's symbols, dropping the family gate of [native matching](#native-matching). A stderr note reports when matches came from a different language than the selector's surface syntax. → docs/05-queries.md "Selector patterns"; Source: `crates/cgx-select/src/family.rs:15`, `crates/cgx-cli/src/main.rs:1988`; See also: [selector](#selector)

<a id="always"></a>**always** (edge condition) — The edge is taken on every execution of the call site; no runtime condition guards it. Used for unconditional calls and for calls inside `finally`/`defer`/cleanup blocks (the call is unconditional once that block is entered; its [transience](#transience) relative to an exception path is computed at query time, not stored in this label). → GM-3; See also: [edge condition](#edge-condition), [transience](#transience)

**any-frontier** — **(deferred)** Informal name for a [type-confidence boundary](#type-confidence-boundary). The `any`-frontier query (Q-30) is not built; the planner rejects the type-reconstruction procedure. → GM-14.6, Q-30; Source: `crates/cgx-cql/tests/call.rs:163`; See also: [type-confidence boundary](#type-confidence-boundary), [lineage type reconstruction](#lineage-type-reconstruction)

<a id="approximation-contract"></a>**approximation contract** — The per-answer statement of *which direction this answer can be wrong, and why*, attached to the answer rather than to any edge. Four fields: `direction` (an [approximation direction](#approximation-direction)); `reasons`, each tagged with the direction it pushes (`over-approx-candidate-set`, `dynamic-dispatch`, `reflective-dispatch`, `unexpanded-macro`, `unresolved-call`, `foreign-function`, `depth-limit`, `below-confidence-floor`, `truncated-path-cap`, `truncated-step-budget`, `summary-budget`, `dropped-max-candidates`, `unresolved-external-calls`, `file-level-granularity`, and others); `scope` (a [negative-completeness scope](#negative-completeness-scope) on negative answers); and `modeled_graph` (a [modeled boundary](#modeled-boundary)). Reasons are derived from what the resolution and the walk did, never from a static per-language table. Not every surface carries one: `explain`, `search`, and `symbols` report symbol facts and skip it. → A3, docs/09 AR-13; Source: `crates/cgx-query/src/contract.rs:112`, `crates/cgx-query/src/contract.rs:307`; See also: [approximation direction](#approximation-direction), [negative-completeness scope](#negative-completeness-scope), [modeled boundary](#modeled-boundary), [freshness envelope](#freshness-envelope)

<a id="approximation-direction"></a>**approximation direction** — The single-word verdict of an approximation contract. `over` — the answer may report edges or paths that cannot occur, because it traversed an over-approximated candidate set. `under` — it may have missed some, because the searched frontier touched a resolution cut, a confidence floor, or a traversal bound. `over_under` — both. `exact` — the traversed subgraph is fully `certain` and cut-marker-free and no bound fired. `exact` is never unqualified: it is always *within* the modeled boundary. → A3, docs/09 AR-13; Source: `crates/cgx-query/src/contract.rs:112`; See also: approximation contract, confidence

<a id="at"></a>**--at** — A flag on the traversal subcommands (`callers`, `callees`, `flows-to`, `flows-from`) that pins the query to a git ref's graph: the ref is materialized in a detached worktree, indexed, and queried, and the [freshness envelope](#freshness-envelope) then measures drift against the pinned tree. `impacted-tests` rejects it with exit 2 because it compares two refs given positionally, and `flows-from` fails under it because the pinned graph has no dataflow layer. The MCP tools have no equivalent. → Q-17; Source: `docs/commands/callers.md:37`, `docs/commands/flows-from.md:44`, `docs/commands/impacted-tests.md:67`, `docs/mcp-tools/README.md:185`, `crates/cgx-cli/src/main.rs:718`; See also: [freshness envelope](#freshness-envelope), [impacted tests](#impacted-tests)

<a id="avoiding"></a>**avoiding** — **(deferred)** A path-quantifier clause in the `cgx` query language (`MATCH ALL … AVOIDING`) that asserts all paths from a source to a sink do NOT pass through a named node. The parser intercepts `MATCH ALL … MUST PASS THROUGH/AVOIDING` and returns a plan error ("not supported in this release"); no ∀-path form evaluates today. → Q-20; Source: `crates/cgx-cql/src/parser.rs:189`; See also: [must-pass-through](#must-pass-through), [path quantifier](#path-quantifier)

**blast radius** — The set of symbols affected by a change to a given function or type: its callers (who depends on it) and callees (what it depends on), traversed transitively to a chosen depth. Blast-radius queries scope the impact of an edit before it is made. → Q-2, Q-13 (depth limits); See also: [reachability](#reachability), [slicing](#slicing)

<a id="blob-oid"></a>**blob OID** — The git content-hash identifier for a single source file at a specific version. `cgx` uses blob OIDs as the primary cache key for per-file graph facts: if a file's blob OID is unchanged across branches or commits, its facts are a cache hit and the file is not re-analyzed. → IX-1; Source: `crates/cgx-store/src/object_store.rs:4`; See also: [branch-aware incremental indexing](#branch-aware-incremental-indexing), [index](#index)

<a id="branch-aware-incremental-indexing"></a>**branch-aware incremental indexing** — The property of `cgx`'s index that lets multiple branches share per-file facts whenever the underlying file content (and therefore blob OID) is the same. Only files whose blob OID changed between two tree OIDs are re-analyzed; unchanged files cost nothing. → IX-1, IX-2, IX-4; Source: `crates/cgx-store/src/object_store.rs:4`; See also: [blob OID](#blob-oid), [index](#index), [prune](#prune)

<a id="build-configuration-variance"></a>**build-configuration variance** — **(deferred)** The dependence of which nodes and edges exist on compile-time conditions such as Rust feature flags, C preprocessor defines, and Go build tags. The edge record has a `cfg_condition` field, but no adapter sets it, so the binary records one configuration and does not label elements by it. → GM-19; Source: `crates/cgx-core/src/edge.rs:151`; See also: [cfg-condition](#cfg-condition)

<a id="by_family"></a>**by_family / by_condition / by_confidence** — The three count maps in an edge breakdown, keyed respectively by edge family (`calls`, `derives_from`), by [edge condition](#edge-condition), and by [confidence](#confidence) tier; `total` is the degree in that direction. They appear on each `symbols` row as an inbound and an outbound breakdown. → docs/mcp-tools/symbols.md:68; Source: `crates/cgx-query/src/symbols.rs:72`; See also: [edge condition](#edge-condition), [confidence](#confidence)

<a id="call-edge"></a>**call edge** — An [edge](#edge) representing the invocation of one callable by another. The wire kinds are `calls`, `calls-virtual`, `calls-closure`, `calls-callback`, `calls-async`, `calls-indirect`; the docs write the same kinds as `calls:virtual` and so on. `spawns` is a separate kind for detached launch. Every call edge carries an [edge condition](#edge-condition). → GM-2.1, GM-9; Source: `crates/cgx-core/src/edge.rs:18`; See also: [edge](#edge), [edge condition](#edge-condition), [virtual dispatch](#virtual-dispatch)

<a id="callers_count"></a>**callers_count / callees_count** — The `explain` counts of direct incoming and outgoing edges of the explained symbol. → docs/mcp-tools/explain.md:33; Source: `crates/cgx-mcp/src/tools.rs:984`; See also: [peer](#peer)

<a id="call-site-node"></a>**call-site node** — The `CallSite` node flavor, identifying a call expression by `(caller, file, line, col)`. The struct is defined but no shipped code constructs it, and the CQL planner rejects the `site` edge property, so there is no `r.site` join; the `site_id` on call edges does ship. Attributes `cfg_block`, `dominating_sites`, `lock_set`, `is_return_site` are reserved and **(deferred)**. → GM-1.4, ADR-01; Source: `crates/cgx-core/src/node.rs:191`, `crates/cgx-cql/src/lower.rs:151`; See also: [dominance](#dominance), [lock set](#lock-set), [site_id](#site_id)

<a id="call--yield"></a>**CALL … YIELD** — The query-language form for invoking a named procedure that returns multiple columns of results. Exactly two procedures exist, both shipped: `cgx.mutation_fanout(value)` (forward `derives-from` reachability out of a value) and `cgx.pedigree(value)` (backward `derives-from` reachability into it). Their yielded columns bind like node properties and compose with a following `WHERE`, `MATCH`, and `RETURN`. Any other name is rejected by the planner, which names the two it knows. → docs/05-queries.md Layer 2 "Procedure calls"; Source: `crates/cgx-cql/src/proc.rs:8`; See also: [procedure](#procedure), [Layer 2](#layer-2), [lineage type reconstruction](#lineage-type-reconstruction), [mutation fan-out](#mutation-fan-out)

<a id="candidate-set"></a>**candidate set** — The set of possible runtime call targets that `cgx` associates with a single call edge when the callee cannot be uniquely resolved. Virtual dispatch, function pointers, and indirect calls produce candidate sets; the set is stored as an attribute on the edge and is bounded by the resolution tier. → GM-2.1, GM-5; Source: `crates/cgx-core/src/edge.rs:147`; See also: [confidence](#confidence), [virtual dispatch](#virtual-dispatch), [cut marker](#cut-marker)

<a id="capture-edge"></a>**capture edge** — **(deferred)** A `calls:closure` edge or a `derives-from` edge annotated with a `closure-capture` escape kind, modelling a closure capturing an enclosing variable. The binary has `calls-closure` edges but no `closure-capture` escape kind, and the Rust, Java and Go adapters do not descend into closure bodies for dataflow. → GM-2.1, DF-16.1, DF-18.2; Source: `crates/cgx-lang-rust/src/extract.rs:1467`, `crates/cgx-lang-java/src/extract.rs:1205`; See also: [closure](#closure), [function value](#function-value)

<a id="certain"></a>**certain** — The highest [confidence](#confidence) tier. An edge is `certain` when it was resolved by direct static binding with no ambiguity — a non-virtual call, a monomorphized Rust generic, or a SCIP occurrence with exactly one target. → GM-5.1; Source: `crates/cgx-core/src/confidence.rs:17`; See also: [probable](#probable), [possible](#possible), [confidence](#confidence)

<a id="cfg-condition"></a>**cfg-condition** — **(deferred)** An attribute recording the build-configuration condition under which an edge is present. The field exists on the edge record (`cfg_condition`); no producer populates it, and only tests set it. A null value means unconditionally present. → GM-19; Source: `crates/cgx-core/src/edge.rs:151`; See also: [build-configuration variance](#build-configuration-variance)

<a id="cgx-toml"></a>**cgx.toml** — The optional per-repository configuration file. The only key the binary honours is `[index] data_flow = false`; it does not declare entrypoints, resource pairs, or framework packs. Source: `crates/cgx-index/src/local.rs:236`; See also: [index](#index)

<a id="cha--rta"></a>**CHA / RTA** — Class-hierarchy analysis and rapid-type analysis, the tier-3 passes. CHA replaces name-method candidate sets (`rule = "name-method"`) with trait-scoped sets (`cha-trait-set`); RTA narrows them to types instantiated in reachable code and raises the surviving group from `possible` to `probable`. Source: `crates/cgx-resolve/src/cha.rs:1`, `crates/cgx-resolve/src/rta.rs:1`; See also: [resolution tier](#resolution-tier), [virtual dispatch](#virtual-dispatch)

<a id="class-matched-sanitization"></a>**class-matched sanitization** — **(deferred)** A rule that clears a taint label only when the sanitizer class matches the sink class. No taint engine exists in the binary; the CQL planner rejects the `sink_class` and `sanitizer_class` properties. → DF-11.2, DF-12; Source: `crates/cgx-cql/src/lower.rs:112`, `crates/cgx-core/src/transform.rs:6`; See also: [sanitizer](#sanitizer), [typed taint](#typed-taint), [sink](#sink)

<a id="closure"></a>**closure** — An anonymous callable that captures variables from its enclosing scope. The binary represents closures as `lambda` nodes ([lambda](#lambda)) and invokes them through `calls:closure` edges; capture tracking and closure-body dataflow are **(deferred)**, so closures do not yet participate in [mutation fan-out](#mutation-fan-out) or pedigree through their captures. → GM-1.1, GM-2.1, DF-18; Source: `crates/cgx-core/src/edge.rs:18`, `crates/cgx-lang-go/src/extract.rs:1010`; See also: [capture edge](#capture-edge), [function value](#function-value), [lambda](#lambda)

<a id="co-change-coupling"></a>**co-change coupling** — The frequency with which two files were changed in the same commit, over an explicit commit range. Reported by `cgx coupling BASE HEAD` as, per file pair, the co-change count and each file's own change count. It is **file-level, not symbol-level**: two files reported as co-changing may have had entirely unrelated symbols edited together, and that over-approximation is permanent and rides in the answer's approximation contract as the `file-level-granularity` reason. Coupling reads committed git history only — it never parses a file, never opens the index, and therefore works on any language, including ones with no adapter. It carries no freshness envelope for the same reason. **On a shallow clone it returns an empty answer at exit 0**, not a partial one. → docs/11-roadmap.md Phase 4; Source: `crates/cgx-diff/src/coupling.rs:49`; See also: MODELED_HISTORY, approximation contract, index-free tool

<a id="coerce"></a>**coerce** — **(deferred)** A `derives-from` transformation kind `coerce(from, to)` marking an implicit type conversion. The `Transform` enum has no `coerce` variant; the class-argument kinds are named in the module comment as reserved. → DF-10.2, DF-17.5; Source: `crates/cgx-core/src/transform.rs:19`, `crates/cgx-core/src/transform.rs:6`; See also: [lineage type reconstruction](#lineage-type-reconstruction), [type-confidence boundary](#type-confidence-boundary)

<a id="commits_considered"></a>**commits_considered** — The `coupling` report count of single-parent commits that contributed co-change counts. Merge commits, root commits and commits over `--max-files-per-commit` are counted separately (`commits_merge_excluded`, `commits_root_excluded`, `commits_large_excluded`) and excluded from this count. → docs/mcp-tools/coupling.md:63; Source: `crates/cgx-diff/src/coupling.rs:121`, `crates/cgx-diff/src/coupling.rs:123`; See also: [co-change coupling](#co-change-coupling), [pairs_total](#pairs_total), [reason code](#reason-code)

<a id="compatible_with"></a>**COMPATIBLE_WITH** — **(deferred)** A query-language predicate that tests structural type compatibility between two types; returns false when the two types share no common subtype. Intended for type-reconstruction queries. The CQL lowering pass rejects it explicitly ("not supported in this release"). → docs/05-queries.md Layer 2 "Predicates"; Source: `crates/cgx-cql/src/lower.rs:240`; See also: [lineage type reconstruction](#lineage-type-reconstruction), [IS EMPTY](#is-empty)

<a id="conditional-edge-condition"></a>**conditional (edge condition)** — The edge is taken only when an explicit boolean branch is true (`if`, `when`, `match` arm, ternary). → GM-3; See also: [edge condition](#edge-condition)

<a id="confidence"></a>**confidence** — A deterministic label on every node and edge that records how well-founded the static resolution was. Exactly three values, ordered `certain > probable > possible`; each is a band assigned by the resolution tier that produced the fact. Confidence is **not** a probability score and must never be read as one, or restated in prose one band stronger than the label says. It is also not merely descriptive: it feeds the approximation contract, where a fully-`certain`, cut-marker-free traversal is what lets an answer report `exact`. → GM-5; Source: `crates/cgx-core/src/confidence.rs:17`; See also: approximation contract, [certain](#certain), [probable](#probable), [possible](#possible), [resolution tier](#resolution-tier)

<a id="confidence_floor"></a>**confidence_floor** — The field of a [negative-completeness scope](#negative-completeness-scope) giving the minimum edge confidence the search required; edges below it were not followed, and `possible` means every edge. The CLI flag that sets it is `--confidence`. → docs/mcp-tools/README.md:89; Source: `crates/cgx-query/src/contract.rs:92`; See also: [searched_edge_kinds](#searched_edge_kinds), [confidence](#confidence)

**contract** — **Collision.** (1) A metadata semantic class meaning the annotation on a symbol carries a value constraint (nullability, precondition, range, type). **(deferred)**: no annotation-to-class lowering exists. → GM-15.1, FW-2; Source: `docs/14-implementation-status-matrix.md:36`. (2) Short for the [approximation contract](#approximation-contract), the per-answer honesty statement (`ApproximationContract`, `crates/cgx-query/src/contract.rs:112`); that sense ships. See also: [metadata fact](#metadata-fact), [semantic class](#semantic-class), [approximation contract](#approximation-contract)

<a id="core-extension"></a>**core-extension** — A status tag applied to features that are high-leverage extensions of the MVP core, derivable from the existing graph structure, and planned from the outset. Core-extension features are not in the initial MVP but are committed to the current design cycle and will be implemented before any roadmap feature. → docs/11-roadmap.md; See also: [schema-room](#schema-room), [roadmap](#roadmap)

<a id="cql"></a>**CQL** — The `cgx` query language reached through `cgx query` and the MCP `graph_query` tool. Keywords: `MATCH`, `WHERE`, `RETURN`, `WITH`, `CALL`, `YIELD`, `ORDER`, `DISTINCT`, `LIMIT`, `ASC`, `DESC`, `AND`, `NOT`, `NONE`, `ANY`, `ALL`; functions `nodes`, `relationships`, `length`, `size`, `select`, `count`, `min`, `max`, `collect`, `last_node`, `position_in`. The planner rejects, with a plan error, unbuilt forms: the edge types `CALLS:super`, `RESOLVES_TO`, `PROVIDES_BODY`, `SHADOWS_FIELD`, `FULFILLS`, `COMPATIBLE_WITH`; unbacked properties (the node property `confidence`; the edge property `r.confidence` ships, and [weakest-link confidence](#weakest-link-confidence) uses it; also `col`, `scope`, `type`, `in_degree`, `out_degree`, `is_exit`, `transformation`, `via`, `taint_label`, `site`); and `IS EMPTY`, `MATCH ALL … MUST PASS THROUGH/AVOIDING`, `CREATE`/`SET`/`DELETE`, `UNWIND`, `OPTIONAL MATCH`, `UNION`, `$x` parameters, and arithmetic. Source: `crates/cgx-cql/tests/rejects.rs:1`, `crates/cgx-cql/src/lower.rs:112`, `crates/cgx-cql/src/eval.rs:1497`, `crates/cgx-cql/src/eval.rs:940`, `crates/cgx-cql/src/eval.rs:1461`, `crates/cgx-cql/src/eval.rs:1468`, `crates/cgx-cql/src/lower.rs:106`, `crates/cgx-cql/src/lower.rs:134`; See also: [Layer 2](#layer-2), [predicate](#predicate), [procedure](#procedure)

<a id="crosses_exceptional"></a>**crosses_exceptional** — A boolean on each `paths` result: `true` when the per-walk transience flag held at any node on the path, which is not the same as the path containing an exception edge (a `spawns` edge resets the flag downstream). → GM-4; Source: `crates/cgx-query/src/engine.rs:214`; See also: [transience](#transience), [exception_transient](#exception_transient)

<a id="cursor"></a>**cursor** — The opaque pagination token of every paginated MCP tool: a 0-based decimal offset string naming the first row of the next page. A response carries `cursor: null` whenever `has_more` is `false`, and an unparseable `cursor` is an [invalid_params](#invalid_params) error. → docs/mcp-tools/README.md:183; Source: `crates/cgx-mcp/src/tools.rs:433`, `crates/cgx-mcp/src/tools.rs:607`; See also: [has_more](#has_more), [max_results](#max_results), [total_matched](#total_matched)

<a id="cut-marker"></a>**cut marker** — An attribute on an edge that signals the static resolution was incomplete and the edge required external evidence or could not be resolved. The values are `reflective`, `dynamic`, `via-DI`, `via-FFI`, `unresolved`, `unexpanded-macro`, `opaque-call` (dataflow through a call site whose callee summary is not yet computed), `truncated-access-path` (a field access path deeper than depth 1, truncated to its base value node), `summary-budget-exceeded` (the IFDS summary pass hit its work budget before reaching a fixpoint), `external` (the call's receiver is an out-of-repo type or module) and `untyped-receiver` (receiver type unknown and the import-visibility rule found no visible target). The last two belong to receiver narrowing and mark dangling references rather than edges. Cut-marker edges are still queryable; the choice to include or exclude them is left to the query author. Every cut marker on a traversed subgraph also becomes an `under` reason in that answer's approximation contract. → GM-5.3; Source: `crates/cgx-core/src/cut.rs:12`; See also: [reflective](#reflective), [via-DI](#via-di), [via-FFI](#via-ffi), unexpanded-macro marker, approximation contract

<a id="dangling-reference"></a>**dangling reference** — A call whose receiver is an out-of-repo type or module, or whose receiver type is unknown and no import-visible target exists. It is marked with the `external` or `untyped-receiver` cut marker and counted rather than emitted as an edge to a resolved target. Produced under `--receiver-narrowing`, which exists for Python and Go. Source: `crates/cgx-core/src/cut.rs:45`, `crates/cgx-cli/src/main.rs:150`, `docs/14-implementation-status-matrix.md:22`; See also: [cut marker](#cut-marker), [receiver narrowing](#receiver-narrowing)

<a id="dataflow-edge"></a>**dataflow edge** — An edge in the graph that encodes value derivation between symbols, primarily `derives-from` edges. Dataflow edges are the backbone of [pedigree](#pedigree), [taint analysis](#taint-analysis), and [forward slicing](#slicing). → GM-2.2, DF-3; Source: `crates/cgx-core/src/edge.rs:18`; See also: [derives-from](#derives-from), [pedigree](#pedigree)

**default method** — **(deferred)** An interface or trait method that supplies a body. The specified record is a `provides-body` fact in the call's [candidate set](#candidate-set); the binary has no `provides-body` edge kind and the planner rejects `PROVIDES_BODY`. → GM-23; Source: `crates/cgx-cql/tests/rejects.rs:7`; See also: [candidate set](#candidate-set), [virtual dispatch](#virtual-dispatch)

<a id="degenerate"></a>**degenerate / degenerate_reason** — Fields of an `impacted-tests` answer: `degenerate` is `true` when the changed set is non-empty and contains no symbol in a language whose tests `cgx` can identify, so an empty `results` is vacuous rather than clean; `degenerate_reason` states why. A degenerate answer exits 4. → docs/mcp-tools/impacted_tests.md:67; Source: `crates/cgx-diff/src/impacted.rs:82`, `crates/cgx-diff/src/impacted.rs:224`; See also: [exit code](#exit-code), [impacted tests](#impacted-tests)

<a id="derives-from"></a>**derives-from** — A directed edge type (from derived value to source value) that encodes how one value was produced from another. The Rust variant is `DerivesFrom` and the edge family token in breakdowns is `derives_from`. Every `derives-from` edge carries a [transformation kind](#transformation-kind) describing the semantic effect of the derivation (e.g. `copy`, `concat`, `parameterize(sql)`). Following these edges backward yields [pedigree](#pedigree); forward yields a [forward slice](#slicing). → DF-3; Source: `crates/cgx-core/src/edge.rs:18`; See also: [pedigree](#pedigree), [taint analysis](#taint-analysis), [transformation kind](#transformation-kind)

**deterministic** — A property of `cgx` answers: the same query against the same commit always produces **byte-identical** output. There is no ordering flag to set — determinism is a property of the engine, enforced by path-sorted file enumeration, dense position-derived node identity (so traversal never depends on hash-map iteration order), a fixed result ordering (`(file, line, col)` for nodes; `(hops, node-id sequence)` for paths), canonical postcard serialization, and content-addressed keys with no wall-clock or random input. It is also why the freshness envelope reports divergence rather than an age.
